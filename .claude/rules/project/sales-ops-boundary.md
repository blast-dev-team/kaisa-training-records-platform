# 영업 / 운영 경계 — 출고완료가 선이다

**영업의 책임은 출고완료까지, 그 뒤는 운영이다.**

조직 규칙이라서가 아니라 **코드가 이미 그렇게 되어 있어서** 이 선을 쓴다 — 영업
인센티브는 `delivery.effective_month`(출고월) 기준으로 집계된다. 출고가 실적을
가르는 사건이다.

---

## 왜 이 문서가 있나

두 화면이 갈려 있는데 **데이터는 하나**다. 그래서 운영이 한 일이 영업의 숫자를
조용히 바꿀 수 있다. 실제로 그런 통로가 하나 열려 있었다.

    운영 렌트료 조정 → long_term.total_amount 덮어씀 → 인센티브 재계산

인센티브가 **정산 스냅샷을 안 쓰기 때문에** 이게 소급된다. `employee_commission_settlement`
테이블에 `total_rental_amount` 컬럼이 있어서 얼려 두는 것처럼 보이지만, 소비하는
쪽은 값을 안 읽는다.

```python
# commission_service.summarize_month
# 정산 스냅샷(freeze) 미사용 — 확정된 달도 항상 live 재계산.
is_settled = user_id in settlement_by_user   # 존재 여부(표시용) — 값은 항상 live
```

의도된 선택이다(정정이 잦아 열어 뒀다). **그래서 더더욱 경계를 넘는 쓰기를 막아야
한다** — 얼려 주는 안전장치가 없다.

---

## 무엇이 어느 쪽인가

| | 영업 (출고완료까지) | 운영 (출고완료 이후) |
|---|---|---|
| 화면 | 통합문의함 · 리드 · 계약 상세 · 출고현황 · 랭킹 | 운영관리 직영/에이전시 · 상품화 관리 |
| 하는 일 | 상담 → 계약 확정 → 차량 매칭 → 출고 | 렌트료 조정 · 납부일 재설정 · 반납 · 재계약 |
| 만드는 청구 | 보증금 · 선납 1회차 · (에이전시)수수료 | 월렌트료 회차 조정 · 위약금 |
| 성과 | 인센티브(출고월 기준) | — |

> 출고완료(`delivery.deliver`) 자체는 영업의 마지막 행동이다 — 월렌트료 N회차를
> **영업이 검토·확정해서** 발행한다. 그 뒤부터 운영이다.

---

## 규칙 ① 운영은 계약의 금액 필드를 바꾸지 않는다

`contract_long_term` 의 두 필드는 **확정 시점 값**이고 영업의 성과 근거다.

| 필드 | 뜻 | 누가 정하나 |
|---|---|---|
| `monthly_amount` | 계약서에 적힌 **기준가** | 확정 |
| `total_amount` | `monthly × months` = **총 렌트료** | 확정 |

`total_amount` 를 읽는 곳이 전부 영업 관점이다 — 인센티브(`commission_service`),
영업 대시보드 통계(`stats/sales_router`), 출고현황 매출액(`delivery/schema`).

**운영이 하는 일은 회차 청구액(`billing_schedule`·`invoice`·line item)만 바꾼다.**
실제 청구 총액이 필요하면 회차 합을 그때 세면 된다. 두 값은 서로 다른 질문에
답한다 — *계약이 얼마짜리였나* / *실제로 얼마를 청구했나*.

```python
# adjust_rent_amount — 회차만 바꾸고 계약 값은 둔다
row.total_amount = new_monthly_amount        # ✅ 회차
contract.long_term.total_amount = after_total  # ❌ 하지 않는다
```

`test_sales_ops_boundary.py` 가 이걸 지킨다. 화면으로는 안 보이는 회귀라서다 —
조용히 달라지는 건 **지난 달 영업 실적**이고, 눈치챌 때쯤이면 인센티브를 지급한 뒤다.

### 총렌트료가 바뀌는 곳은 넷뿐이고 전부 영업 단계다

| 함수 | 시점 |
|---|---|
| `confirm_from_lead` | 리드 → 계약 생성 |
| `update_contract` | 계약 조건 수정 |
| **`confirm_contract`** | **계약 확정 — 사실상 여기서 결정** |
| `renew_contract` | 연장(새 계약이라 별개) |

출고완료(`delivery.deliver`)는 안 건드린다.

---

## 규칙 ② 편집 잠금선은 이 경계와 다르다 — 섞지 말 것

"영업 책임이 출고까지" 라고 해서 **출고를 편집 잠금선으로 쓰면 안 된다.**
한 번 그렇게 했다가 되돌린 이력이 있다 (TK-17259, PRD v1.62).

> 인도를 전 그룹 공통 차단선으로 뒀는데, 인도는 "돈이 오갔다"는 뜻이 아니다.
> 확정 장기계약 960건 중 **보증금이 미수납인데 인도만으로 잠긴 계약이 852건**이었다.

현재 차단선은 **돈**이다 (`locked_term_group`):

- **수납됨** — 받은 돈은 소급하지 않는다
- **월렌트료가 이미 발행됨** — 조건을 바꾸면 발행된 N회차를 다시 만들어야 하는데 그 흐름이 없다

| | 무엇을 정하나 |
|---|---|
| **책임 경계**(이 문서) | 누가 그 뒤를 관리하나 · 누구의 성과인가 |
| **편집 잠금선**(`locked_term_group`) | 지금 이 필드를 고쳐도 안전한가 |

앞은 조직, 뒤는 데이터 안전성이다. 같은 선일 이유가 없다.

---

## 알려진 어긋남 — 고치지 않은 것

**영업 계약 상세의 총렌트료와 인센티브의 총렌트료가 다른 값을 쓴다.**

```
계약 상세 화면   monthly × months   (contract-info-panel.tsx, FE 재계산)
인센티브        total_amount        (없으면 monthly × months 로 폴백)
```

의도한 분기가 아니다. 화면이 2026-05-22 에, 인센티브가 2026-08-19 에 따로 쓰였고
아무도 맞춰본 적이 없다. 인센티브가 저장값을 택한 이유는 주석에 남아 있다 —
**이관 계약은 `monthly_amount = 0` 이라 곱셈이 0을 낸다.**

프로덕션 실태(확정 장기계약 1,065건):

| 출처 | 계약 | 두 값 불일치 | `monthly_amount = 0` |
|---|---:|---:|---:|
| 이관분(2026-05-31) | 649 | **238** | 283 |
| 운영 중 생성 | 416 | **0** | 0 |

**운영 중 생긴 계약은 완전히 일치한다.** 어긋남은 전부 이관 데이터다. 다만 그
283건은 **계약 상세가 총렌트료를 `0원` 으로 보여주고 있다** — 저장값이 맞고 화면이
틀렸다. 고치려면 화면을 `total_amount` 로 바꾸면 되는데, 이관 데이터 정합성
점검이 먼저라 미결로 둔다.

---

## 체크리스트 — 운영 쪽 코드를 쓸 때

- [ ] `contract_long_term` 의 `monthly_amount` · `total_amount` 에 쓰고 있지 않은가
- [ ] 바꾸는 것이 회차(`billing_schedule` · `invoice`)로 한정되는가
- [ ] 금액을 바꾼다면 **사유를 받고 활동이력에 남기는가** (`rent_amount_adjusted`)
- [ ] 출고를 편집 잠금선으로 새로 쓰고 있지 않은가 (`locked_term_group` 을 쓴다)

## 미결

1. 계약 상세 총렌트료를 `total_amount` 로 통일할 것인가 — 이관 283건이 0원으로
   보이는 문제가 걸려 있다. 데이터 점검이 먼저다.
2. 인센티브 정산 스냅샷을 살릴 것인가 — 지금은 정정 편의를 택해 live 재계산이다.
   지급 후 숫자가 달라지는 게 문제가 되면 그때 다시 본다.
3. 이미 조정된 계약 2건(`LT-2024-0013` · `LT-2025-0146`)의 `total_amount` 는
   덮인 채로 뒀다. 둘 다 이관분이라 "원래 값" 이 무엇인지 계약서 대조가 필요하다.
