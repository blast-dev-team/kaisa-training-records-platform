# 사고대차 — 서비스 종료 예정

**사고대차(`accident_rent`)는 서비스를 접기로 했다.** 새 기능·개선의 대상이 아니다.
이 판단을 여기 적어 두는 이유는, 코드만 보면 **정반대로 보이기 때문**이다.

---

## 지금은 최고조다 — 그래서 헷갈린다

2026-08-31 프로덕션 기준.

| | |
|---|---:|
| 사고대차 계약 | 161 |
| **진행 중(반납 안 됨)** | **160** |
| 이번 달 신규 계약 | 42 |
| 사고대차 리드 | 436 |
| **이번 달 신규 리드** | **171** |
| 청구서 (미수납 0) | 49 |

**오늘도 계약이 만들어지고 있다.** "죽은 도메인" 이 아니라 "곧 접을 건데 아직 돌아가는"
상태다. 그래서 화면을 끄거나 코드를 지우는 건 **지금 할 일이 아니다.**

코드 규모도 작지 않다 — **FE 113 파일 · BE 35 파일** (`*accident*` 기준).

---

## 그래서 무엇을 하고 무엇을 안 하나

| | |
|---|---|
| ✅ **버그는 고친다** | 진행 중 계약 160건이 돌아간다. 깨지면 실무가 멈춘다 |
| ✅ **깨지지 않게 유지한다** | 공용 코드를 바꿀 때 사고대차 화면도 안 깨지는지는 확인한다 |
| ❌ **새 기능을 넣지 않는다** | 영업(직영·에이전시)에 넣은 기능을 사고대차에 미러링하지 않는다 |
| ❌ **개선·리뉴얼 하지 않는다** | UI 정리·리팩토링 대상에서 뺀다 |
| ❌ **아직 지우지도 않는다** | 종료 시점이 안 정해졌다. 데이터가 계속 쌓이는 중 |

### 기능을 넣을 때 — 미러링을 기본값으로 두지 않는다

영업 CRM 과 사고대차 CRM 은 **화면이 통째로 나뉘어 있다**(`views/leads` ↔
`views/accident-leads` 처럼 쌍으로). 예전엔 한쪽에 기능을 넣으면 다른 쪽에도
넣는 게 기본이었는데, **이제 아니다.**

넣지 않은 것을 **말없이 빼먹지는 말고**, 커밋·PR 에 한 줄 적는다 —
"사고대차는 종료 예정이라 미러링하지 않음".

---

## 실무적 함의 — 정리 계획이 달라진다

`consultation-memo.md` 가 상담일지 패널의 중복 정리를 숙제로 남겨 뒀다. 그 문서는
**3벌**이라고 적었지만 지금은 **6벌**이고, **그중 3벌이 사고대차다.**

```
영업     문의(12) · 리드(16) · 계약(27)      ← 통합 대상
사고대차  문의(8)  · 리드(12) · 계약(14)      ← 없앨 것. 통합에 끼우지 않는다
                                                (괄호 = resolveActivityContent 의 case 수)
```

**없앨 코드를 정리하는 데 시간을 쓰지 않는다.** 공용화·리팩토링 범위를 잡을 때
사고대차 3벌은 빼고 센다.

---

## 종료 시점

**미정이다.** 정해지면 여기에 적는다. 그전까지는:

- 진행 중 계약 160건이 **반납·정산까지 끝나야** 화면을 끌 수 있다
- 데이터(계약·리드·청구서)는 지우지 않는다 — 실적·정산 이력이다
- DB 스키마(`contract_accident_rent`, `lead.lead_type`, `accident_*` 테이블)도 그대로 둔다
