# CRM QA Intake — 트리아지→수정 (기본: 직접)

사람이 준 버그/QA를 처리한다. **기본은 이 컨텍스트에서 직접** 따른다 — 서브에이전트 안 띄움(`.claude/CLAUDE.md §5`).

## 흐름 (직접 따르는 체크리스트)

### ① 트리아지
- 리포트를 개별 이슈로 분해(중복 합치기).
- **재현**: 코드 추적/앱 구동으로 재현 시도 → `재현됨` / `재현 안 됨` / `정보 부족`.
- **근본 원인**: 재현된 건 파일:라인 수준으로 규명. **증상 패치 금지** — 원인 짚은 뒤에만 고침.
- **버그 vs 기획 분류**: 상태머신/트리거 맵 변경, 신규 상태·필드가 필요하면 **버그 아님 = 기획**. 이땐 개발로 넘기지 말고 `crm-feature` 흐름(기획)으로.
- **우선순위**: blocker(데이터오염·크래시·결제) > major(핵심 플로우) > minor(UI·문구).
- 재현 안 됨/정보 부족은 **추측으로 고치지 말고** 물어볼 항목 정리(사용자 or QA 회신용).

### ② 확인 게이트
- 우선순위·범위 확인. 정보 부족 건은 보류(QA 되물음).

### ③ 수정
- 승인된 이슈만 **근본원인 수정**. 이슈 단위 atomic, **범위 밖 리팩터링 금지**.
- 기존 도메인 패턴·`.claude/rules/*` 준수.

### ④ self-verify
- 이슈별 재현 시나리오로 검증 + `pnpm check-types`. 회귀 확인(특히 공용 코드).

### ⑤ 마무리
- **QA 회신용**으로 정리(이슈별 고침/보류/정보대기 + 근거). 커밋은 사용자 요청 시만.
- ClickUp 티켓에 올릴 때는 **`clickup-qa-report`** 형식을 따른다 — 읽는 사람이 비개발자
  PM 이다. 남이 만든 티켓엔 댓글, 내가 만든 QA 티켓엔 본문. 트리아지 결과(고침/기획/재현안됨)가
  그대로 댓글 세 갈래에 붙는다.

## 서브에이전트로 올릴 때만 (예외)
**틀리면 비싼** 수정(결제·정산·프로덕션·공용 페이지)일 때만, **사용자에게 먼저 알리고**, `general-purpose` 서브에이전트로 **독립 검수**를 스폰한다(`model: opus`, 적대적·두 렌즈·오탐 금지·심각도순 — `crm-feature` 스킬의 독립 검수 지시 참고). 그 외 트리아지·판단은 메인에서 직접.

## 원칙
- **근본 원인 우선**(증상 패치 금지). **추측으로 안 고침**. **범위 고정**(QA 지적만). trivial·명확한 건은 무조건 직접.
