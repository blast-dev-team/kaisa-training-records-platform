# ClickUp 작업 결과 보고

**고친 다음 무엇을 어떻게 써서 올릴지**를 다룬다.
처리 절차(재현→원인→수정→검증)는 `crm-qa-intake`, CLI·티켓 계층은 `clickup` 스킬.

## 읽는 사람 — 비개발자다

PM·기획·운영이 본다. 개발자가 아니다. 이 전제가 형식을 전부 결정한다.

- **결론이 맨 위.** 고쳤나 / 못 고쳤나 / 버그가 아닌가.
- **원인은 한두 문장.** 함수명·파일경로·커밋해시를 나열하지 않는다.
  ("`start_date` 를 인도 신호로 써서" 정도는 OK — 필드 이름은 PM 도 아는 개념)
- **영향은 숫자로.** "많이 열렸어요" ✗ → "20건 → 50건" ✓
- **확인 방법은 실제 데이터로.** "테스트해보세요" ✗ → "`LT-2025-0140` 열어서 [편집] 눌러보세요" ✓
- 테스트 개수·뮤테이션·타입체크는 **맨 아래 한 줄**로. 없어도 되지만, 있으면 신뢰가 붙는다.

---

## 세 가지 상황

| 상황 | 어디에 | 왜 |
|------|--------|-----|
| **남이 만든 티켓에 답한다** (대부분) | **댓글** (A) | 남의 본문을 덮으면 원 제보 내용이 사라진다 |
| 티켓은 있는데 **본문이 비어 있다** | **본문** (B) | 채우는 것이지 덮는 게 아니다 |
| **티켓 자체가 없다** | **생성** (C) | 작업 중 튀어나온 별건 |

> 본문이 이미 있는 티켓에 `update --desc-file` 을 쓰면 **통째로 덮어쓴다.**
> 남의 티켓에는 쓰지 않는다. 꼭 본문에 넣어야 하면 `--append`.

---

## A. 댓글 — 남이 만든 티켓에 답할 때 (기본)

결과에 따라 세 갈래다. `crm-qa-intake` 의 트리아지 결과와 1:1로 붙는다.

### A-1. 고쳤다

```md
고쳤습니다. PR: #539

**원인**
차량 인도 여부를 계약 시작일로 판단하고 있었어요. 시작일은 인도 말고도 채워져서
(계약 확정일이 들어가거나 '8월19일' 같은 텍스트가 들어감), 인도도 안 된 계약이
'인도됨'으로 잡혀 수정 버튼이 사라졌어요.

**고친 것**
실제 인도일 기준으로 판정하게 바꿨어요.

**영향**
미인도 확정계약 중 조건 수정 가능: 20건 → 50건

**확인 방법**
스테이징에서 `LT-2025-0140` 계약 상세 → 계약 조건 카드에 [편집] 버튼이 보이면 정상이에요.

배포는 백엔드 태그가 먼저 나가야 해요.
```

**PR 링크만 남기는 경우**도 있다. 원인이 자명하고 제목만으로 충분할 때:

```md
고쳤습니다. PR: #539 — 제조사 순서를 현대·기아·제네시스 먼저로.
```

### A-2. 버그가 아니다 (기획·의도된 동작)

되묻지 말고 **왜 그런지 + 바꾸려면 무엇이 필요한지**까지 적는다.

```md
현재 동작이 의도된 거예요.

에이전시 계약은 공카가 보증금을 직접 받지 않아서 청구서를 만들지 않아요.
화면의 '보증금 (참고)' 라벨이 그 뜻이에요.

바꾸려면 에이전시 보증금도 공카가 청구·수납하는 걸로 정책이 바뀌어야 해서,
기획 결정이 먼저 필요해요. 필요하시면 기획 티켓으로 올릴게요.
```

### A-3. 재현이 안 된다 / 정보가 부족하다

**추측으로 고치지 않는다.** 무엇을 해봤는지 + 무엇이 필요한지.

```md
재현이 안 돼서 확인 부탁드려요.

**해본 것**
스테이징 계약 12건(직영·에이전시 섞어서)에서 같은 순서로 눌러봤는데 정상 동작했어요.

**필요한 것**
- 계약번호 (LT-2026-XXXX)
- 어느 계정으로 보셨는지
- 가능하면 화면 캡처

이 세 개 주시면 바로 다시 볼게요.
```

## B. 본문 — 티켓은 있는데 비어 있을 때

스프린트에 제목만 올라와 있는 티켓, 또는 내가 만든 작업 티켓.
**여러 PR·여러 문제를 묶는 단위**일 때 쓴다 — 댓글 한 줄로 안 되는 경우.

> 본문이 이미 차 있으면 B 가 아니다. 남의 글을 덮지 말고 **A(댓글)** 로 간다.

```md
# {실제 작업 범위를 담은 제목}

한 단락 — 무엇을 왜 했는지. 제보 문장을 그대로 인용하면 맥락이 산다.

기획: {PRD 링크} (있으면)

---

## 1. {문제 이름} ✅

**PR:** #539 (머지됨)

문제 설명 두세 문장. 왜 그렇게 됐는지까지.

| | 전 | 후 |
|---|---:|---:|
| {지표} | 20 | **50** |

---

## 2. {두 번째 문제} ✅
...

---

## 영업이 스스로 할 수 있는 것 / 문의해야 하는 것

| 상황 | 처리 |
|---|---|
| {흔한 실수} | ✅ 화면에서 직접 |
| {잠기는 조건} | ❌ 개발팀에 요청 |

## 확인 방법 (스테이징)

- [ ] `LT-2025-0140` — {무엇을 보면 되는지}
- [ ] 회귀: {같은 코드를 타는 다른 기능}

## 배포 순서 ⚠️
(순서가 있으면. 없으면 생략)

## 검증
BE 252 · FE 178 tests / 마이그레이션 불필요

## 미결
1. 결정이 필요한 것 — 선택지까지.
```

**섹션은 필요한 것만.** 배포 순서가 없으면 그 절을 지운다. 빈 절을 남기지 않는다.

## C. 티켓을 새로 만들 때

작업 중 **별건이 튀어나왔을 때**가 대부분이다 — 고치다 보니 나온 다른 문제, 지금은
안 하지만 남겨야 하는 것.

```bash
create --name "[QA] 계약 상세 — 보증금 회차 수정 안 됨" \
       --parent TICKET-17239 --desc-file body.md
```

- **만들기 전에 `search` 로 중복을 본다.** 같은 주제 티켓이 있으면 새로 만들지 말고
  거기 댓글로 붙인다. 티켓이 갈리면 논의도 갈린다.
- `--parent` 를 빠뜨리지 않는다. 루트에 뜨면 아무도 못 찾는다.
- 상태는 기본값(`to do`)으로 두고 사람이 정하게 한다.
- 본문은 B 템플릿을 줄여서 — **목적 · 재현/상황 · 미결** 정도면 충분하다.
  나중에 손댈 때 상세로 승격한다.

> 별건인지 아닌지 애매하면 **원 티켓 댓글에 먼저 적고** 사용자에게 티켓으로 뺄지 묻는다.
> 티켓을 늘리는 건 되돌리기 번거롭다.

## 문장 규칙

| ✗ | ✓ |
|---|---|
| "`update_contract` 의 `_TERM_EDIT_FIELDS` 를 분리" | "기간·월대여료와 보증금을 따로 판정하게 나눴어요" |
| "수정되었습니다" | "고쳤습니다" |
| "확인 바랍니다" | "확인 부탁드려요" / "이렇게 눌러보시면 돼요" |
| "정상 작동합니다" | "`LT-2025-0140` 에서 확인했어요" |
| "다수의 계약에 영향" | "36건" |

- 존댓말·해요체. 보고서 말투(~하였음, ~바람)를 쓰지 않는다.
- 이모지는 상태 표시(✅ ⚠️ ❌)에만. 장식으로 쓰지 않는다.
- PR 은 `#539` 로 쓴다 — ClickUp 이 자동 링크하지 않으므로 전체 URL 이 나을 때도 있다.

## 하지 말 것

- **남의 티켓 본문을 덮어쓰기.** 원 제보가 사라진다. 댓글이나 `--append`.
- **상태·담당자 임의 변경.** 사람이 관리하는 신호다. 바꿀지 물어본다.
- **안 해본 걸 했다고 쓰기.** "테스트 완료" 대신 실제로 확인한 것만.
- **확인 방법을 "테스트해주세요" 로 끝내기.** 계약번호·화면·눌러야 할 것까지.
- 기획 문서·PRD 내용을 본문에 복제. 링크로 건다 (복제하면 갈린다).

## 절차

```
1. get 으로 현재 티켓 확인       ← 본문이 있는지, 누가 만들었는지
   (티켓이 없으면 search 로 중복부터 확인)
2. 상황 판단 → 댓글(A) / 본문(B) / 생성(C)
3. 초안을 스크래치패드 .md 로 작성
4. 사용자 확인 후 반영
   댓글: comment TICKET-XXXXX --desc-file note.md
   본문: update  TICKET-XXXXX --desc-file body.md [--append]
   생성: create  --name "..." --parent TICKET-XXXXX --desc-file body.md
5. get 으로 반영 확인
6. 상태를 바꿔야 할 것 같으면 사용자에게 물어본다 (임의로 안 바꿈)
```

제목이 내용과 안 맞으면 **알린다**. 바꾸기 전에 그 주제의 다른 티켓이 있는지 `search` 로 확인한다
— 이름을 바꾸면 원래 작업 항목이 목록에서 사라질 수 있다.
