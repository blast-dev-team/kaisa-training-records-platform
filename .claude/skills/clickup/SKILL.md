# ClickUp 티켓 관리

공카 CRM 태스크는 ClickUp **BOYD > Client Project Tasks > Gongcar** 리스트에서 관리한다.
읽기·쓰기 모두 **공식 API(v2)** 로 한다 — 웹 페치나 브라우저로 긁지 않는다.

이 리스트는 단순 할 일 목록이 아니라 **제품 기획 문서**로도 쓴다.
대분류 티켓 = 마일스톤, 화면 티켓 = 그 화면의 기획서다. 본문 작성 규칙(§4)이 중요한 이유.

## 1. CLI

```bash
python3 .claude/skills/clickup/clickup.py <command>
```

토큰은 `CLICKUP_TOKEN` 환경변수 → 없으면 `ref/clickup-api.md` 에서 자동으로 읽는다
(`ref/` 는 gitignore 대상이라 커밋되지 않는다). 팀·리스트 ID 는 스크립트에 하드코딩돼 있다.

| 명령 | 용도 |
|---|---|
| `get TICKET-17182` | 티켓 상세 + 설명(markdown 원문) |
| `get TICKET-17182 --json` | 원본 JSON (커스텀필드·담당자 등 확인용) |
| `tree TICKET-17182 [--depth 1]` | 하위 티켓 트리. 설명 없는 티켓은 `← 설명 없음` 표시 |
| **`nav [--todo]`** | **사이드바 메뉴 ↔ 티켓 대조** (§2). `--todo` 는 티켓·본문 없는 것만 |
| `search "출고현황"` | 이름·설명 키워드 검색 |
| `list --status "in progress"` | 리스트 전체 (상태·부모 필터) |
| `statuses` | 사용 가능한 상태값 |
| `comments TICKET-17182` | 댓글 조회 |
| `create --name "..." --parent TICKET-17182 --desc-file body.md` | 하위 티켓 생성 |
| `update TICKET-17182 --desc-file body.md [--append] [--status "..."] [--name "..."]` | 설명·상태·이름 수정 |
| `comment TICKET-17182 --desc-file note.md` | 댓글 작성 |
| `delete TICKET-17182 --yes` | 삭제 |

- 티켓 ID 는 `TICKET-17182`(custom id) / `86eyhg97f`(내부 id) 둘 다 받는다.
- 설명은 **markdown 그대로** 들어가고 그대로 읽힌다 (표·체크박스·코드블록 OK).
- 본문이 길면 `--desc`(인라인) 대신 스크래치패드에 `.md` 파일을 쓰고 `--desc-file` 로 넘긴다.
- `update --desc*` 는 **기존 설명을 통째로 덮어쓴다.** 이어붙이려면 `--append`.

## 2. 티켓 계층 — 사이드바와 1:1

```
CRM (TICKET-15651)                      ← 루트
├── 마스터 (TICKET-17182)                ← 대분류 = 사이드바 대메뉴 · 마일스톤
│   ├── 직원 관리 (17183)                 ← 화면 = 사이드바 하위메뉴 · 기획서
│   └── 차량 관리 (17188)                 ← 사이드바 sub-group
│       └── 제조사*모델 관리 (17189)
│           └── [FE] 모델 라인 편집 모달     ← 개발 티켓 (§4-4)
└── ...
```

대분류·화면 티켓은 사이드바
([sidebar.tsx](../../../frontend/apps/crm-fe/src/widget/sidebar/ui/sidebar.tsx) 의
`NAV_SECTIONS_RAW`)와 1:1로 맞춘다. **이 대조는 `nav` 가 자동으로 해준다.**

```bash
python3 .claude/skills/clickup/clickup.py nav --todo
```

```
영업 CRM                            TICKET-16766 [in progress] (map)  ← 본문 없음
  통합 문의함  /sales/inquiries       ✗ 티켓 없음
  ...
대분류 9/14 · 하위 26/70 · 본문 없는 티켓 16
```

- `(map)` = `nav-map.json` 에 명시된 매핑, `(auto)` = 이름이 같아 자동 매칭
  (공백·`·`·`*` 무시 — 사이드바 `구매·매각` ↔ 티켓 `구매*매각` 이 자동으로 붙는다)
- `✗ 티켓 없음` = 만들어야 할 것, `← 본문 없음` = 기획을 채워야 할 것

### nav-map.json

이름이 달라 자동 매칭이 안 되는 것만 적는다. 대분류는 자동 매칭 대상이 아니라 항상 적는다.

```json
{ "master-approvals": "TICKET-17187" }   // 사이드바 '가입 승인' ↔ 티켓 '승인 관리'
```

새 티켓을 만들었는데 이름이 사이드바 라벨과 다르면 여기에 추가한다.
사이드바 메뉴가 늘거나 이름이 바뀌면 `nav` 를 다시 돌려 차이를 확인한다.

### 사이드바 밖 티켓

QA/QC(15684), 데이터 마이그레이션(16817), 추가기능 및 고도화(16657) 처럼
화면이 아닌 트랙은 사이드바에 대응이 없다. `nav` 에 안 잡히는 게 정상이다.

## 4. 본문 작성 규칙

### 4-1. 대분류(마일스톤) 티켓

이 메뉴가 무엇을 책임지는지 + 화면 목록 + 전체에 걸린 원칙·미결.
개별 화면 얘기는 하위 티켓에 넘기고 여기선 **표로 인덱싱만** 한다.
기준 샘플: [TICKET-17182 마스터](https://app.clickup.com/t/86eyhg97f)

```md
## 목적
한 단락. 이 메뉴가 무엇을 책임지고, 무엇을 책임지지 않는가.

## 화면 구성
사이드바 `{대메뉴}` (`sidebar.tsx` > `NAV_SECTIONS_RAW`) 와 1:1.

| # | 화면 | 경로 | 티켓 | 구현 |
|---|---|---|---|---|
| 1 | 직원 관리 | `/master/members` | TICKET-17183 | ✅ |
| 2 | 차량 관리 (그룹) | — | TICKET-17188 | — |

## 공통 원칙
이 메뉴 전체에 걸리는 규칙. 예: "삭제보다 비활성화", "참조 중이면 삭제 차단".

## 권한 — AS-IS
| 레이어 | 현재 상태 |
|---|---|
| FE 사이드바 | `adminOnly` 없음 → 전 직원 노출 |
| BE `user` | 쓰기=`require_admin` |

## 미결
1. 결정이 필요한 항목 — 선택지까지.
```

### 4-2. 화면 티켓

**스텁 → 상세** 2단계로 간다. 전 화면을 먼저 스텁으로 덮고, 손대는 화면부터 상세로 승격한다.

**스텁** (신규 화면 티켓의 최소 형태 — 이것만으로도 `← 본문 없음` 은 벗어난다)

```md
## 목적
한 줄.

## 화면
- 경로: `/sales/leads`
- 파일: `views/leads/ui/leads-page.tsx`

## 기능
- 목록 · 필터 · 상세 진입
- (아는 만큼만. 모르는 건 적지 않는다)

## 미결
- 확인 필요한 것
```

**상세** (기준 샘플: [TICKET-17187 승인 관리](https://app.clickup.com/t/86eyhg9gb))

```md
## 목적
## 화면            경로 · 파일 · 진입점
## 기능 명세        컬럼 · 액션 · 문구. 액션은 표로 (액션 | API | 결과)
## 비즈니스 규칙     상황별 응답 표 (409 ALREADY_ACTIVE 등 에러코드까지)
## API             메서드 | 경로 | 권한 표
## 미결
```

바뀐 이력 중 **왜 그렇게 됐는지**가 중요한 건 본문에 남긴다
(예: "거절은 전용 API 여야 한다 (TK-17155) — 예전엔 deleteUser 재사용이라 …").

### 4-3. QA·작업 결과 보고

고친 결과를 티켓에 올리는 건 형식이 다르다 — **읽는 사람이 비개발자 PM** 이고,
기획서가 아니라 "무엇을 고쳤고 어떻게 확인하나" 가 본론이다.
남이 만든 티켓엔 **댓글**, 내가 만든 QA 티켓엔 **본문**.

→ **`clickup-qa-report`** 스킬을 따른다.

### 4-4. 개발 티켓

`[BE]` / `[FE]` / `[Integration]` 접두사 + DoD 체크리스트.
상세 템플릿은 [task-management.md](../../rules/task/task-management.md) 참고
(단, 그 문서가 말하는 `tasks/` 동기화 스크립트는 현재 레포에 없다 — 이 CLI 로 대체).

구현 상태 표기: ✅ 완료 · ⚠️ 부분 · 🔲 미착수

### 4-5. 공통 원칙

- **코드에서 읽은 사실만 쓴다.** 경로·파일·API·에러코드는 실제로 확인하고 적는다.
  추측한 스펙을 기획서로 박아 두면 나중에 그게 근거로 쓰인다.
- **모르는 건 `## 미결` 로 내린다.** 빈칸을 그럴듯하게 메우지 않는다.
- 구현이 기획과 다르면 기획을 고치지 말고 **AS-IS 를 적고 미결에 올린다** (마스터 티켓의 "권한 — AS-IS" 처럼).
- DB·정산 관련은 [docs/crm/prd/](../../../docs/crm/prd/) 와 `docs/db-schema.md` 를 링크로 걸고
  본문에 복제하지 않는다. 복제하면 갈린다.

## 5. 작업 절차

**사이드바 기준으로 티켓 채우기**

```
1. nav --todo            → 무엇이 비었는지 확인
2. 대분류 누락분 create   → 4-1 템플릿, 사이드바 라벨과 같은 이름으로
3. 화면 누락분 create     → --parent 대분류, 4-2 스텁
4. 이름이 라벨과 다르면 nav-map.json 에 추가 → nav 로 재확인
5. 대분류 본문의 화면 구성 표에 새 티켓 번호 반영
```

**기존 티켓 상세화**

```
1. get 으로 현재 본문 확인   ← 반드시 먼저. update 는 덮어쓴다
2. 코드 확인 (화면 파일 · 라우터 · 백엔드 라우터/서비스)
3. 초안을 스크래치패드 .md 로 작성 → 사용자 확인
4. update --desc-file (이어붙이는 경우 --append)
```

## 6. 주의

- **쓰기 전 현재 내용을 먼저 `get` 으로 읽는다.** 이미 내용이 있으면 사용자에게 알리고
  덮어쓸지(`--desc-file`) 이어붙일지(`--append`) 확인한다.
- **`create` 전에 `search` 로 중복을 확인한다.** 같은 주제 티켓이 이미 있으면 새로 만들지
  말고 거기에 붙인다. 티켓이 갈리면 논의도 갈린다.
- **제목을 바꾸기 전에도 `search`.** 이름을 바꾸면 원래 주제가 목록에서 사라진다 —
  그 주제의 다른 티켓이 있는지 먼저 본다.
- 여러 티켓을 한 번에 채울 때는 파일로 초안을 쓰고 **사용자 확인 후** 반영한다.
- 삭제는 되돌릴 수 없다. 사용자가 명시적으로 요청할 때만.
- 상태 변경은 사람이 관리하는 신호다. 요청 없이 바꾸지 않는다.
- 담당자 배정도 건드리지 않는다.
