# 커밋 · PR 규격

**형식**은 `rules/project/git-commit.md`(레이어 접두사)와 `rules/common/pull-request.md`(PR 템플릿)에 있다.
여기는 **순서와 탐지** — 매번 손으로 확인하다 빠뜨리는 것들이다.

## 0. 사실부터 모은다

```bash
bash .claude/skills/crm-ship/check.sh
```

브랜치 · dev 대비 위치 · 변경 레이어 · **마이그레이션** · **배포 순서** 를 한 번에 찍는다.
읽기 전용이라 아무것도 안 고친다. 판단은 사람이 한다.

---

## 1. 커밋 전 검증 — 건너뛰지 않는다

**한 번 dev 를 깨뜨린 적이 있다.** vitest 만 돌리고 커밋했는데 `tsc` 에서 4건이 났다.
빌드는 `tsc --noEmit && vite build` 라 **테스트 통과 ≠ 빌드 통과** 다.

| 바꾼 곳 | 돌릴 것 |
|---|---|
| `backend/` | `uv run pytest -q` · `uv run ruff check <바꾼 파일>` |
| `frontend/` | `pnpm exec tsc --noEmit` · `pnpm vitest run` · **`pnpm build`** |

- **lint 는 바꾼 파일만 본다.** 도메인 전체를 돌리면 기존 오류에 묻힌다.
  전체를 돌렸다면 `git stash` → `origin/dev` 기준으로 재확인해 **내 것인지 기존 것인지** 가른다.
- 순수 함수를 새로 만들었으면 **뮤테이션 테스트**로 그 테스트가 실제로 무는지 본다
  (조건 뒤집기 → 실패하는지 → 원복).
- 돈·상태 전환처럼 틀리면 비싼 코드는 **로컬 DB 로 실제 실행**해 본다. 순수 함수
  테스트로는 배선 누락(예: `schedule.invoice_id` 미설정)을 못 잡는다. 실행 후 **원복**한다.

## 2. 브랜치

- `dev` · `main` 에 직접 커밋하지 않는다. `type/짧은-설명` 으로 판다.
- **`dev` 가 앞서갔으면 리베이스한다.** `check.sh` 가 겹치는 파일을 보여준다 —
  0개면 충돌 없이 끝난다.
- 리베이스 후 **검증을 다시 돌린다.** 남의 변경과 합쳐진 상태는 처음 보는 상태다.

## 3. 커밋 메시지

```
type(layer/scope): 설명
```

레이어는 `check.sh` 의 "변경 레이어" 를 그대로 쓴다 — `be` · `fe` · `ci` · `infra`.
**BE·FE 가 함께 걸리면 커밋을 나누는 게 원칙**이다(`project/git-commit.md`).
불가피하면 주된 레이어 하나로.

본문에 남길 것:
- **왜** 그렇게 했는지. 무엇을 했는지는 diff 가 말한다
- 판단 근거가 된 **실측 숫자** (예: "운영 9명 전원 같은 팩스")
- 되돌리면 깨지는 이유 — 나중에 누가 "이거 왜 이래?" 할 지점

## 4. PR 본문 — 반드시 들어가는 두 가지

### 마이그레이션

**있든 없든 명시한다.** 안 적으면 리뷰어가 확인하러 파일을 뒤져야 한다.

```md
**스키마 변경 없음 → 마이그레이션 불필요**
```

있으면 크게:

```md
## ⚠️ 마이그레이션 필요

`backend/api/alembic/versions/xxxx_add_foo.py` (`abc123` → `def456`)

프로덕션 alembic 은 **수동**이다(스테이징은 자동). 배포 후 실행해야 한다.
```

- CI 가 **single head** 를 검사한다 — `down_revision` 이 현재 head 를 가리키는지 확인
- 컬럼 추가는 `nullable=True` 또는 `server_default` (`project/db-planning.md`)

### 배포 순서 (BE·FE 동시 변경일 때만)

```md
## 배포 순서 ⚠️

**BE 태그가 FE 보다 먼저.** FE 는 dev 머지로 Amplify 가 자동 배포하고,
BE 는 `be-staging-v*` / `be-prod-v*` 태그가 수동이다.
역순이면 화면은 열리는데 서버가 거부한다.
```

BE 만·FE 만이면 이 절을 넣지 않는다. 빈 절을 남기지 않는다.

## 5. PR 본문 — 나머지

`rules/common/pull-request.md` 템플릿 위에 이것들을 얹는다.

- **변경 이유**를 제보 문장으로 시작하면 맥락이 산다 ("돈을 안 받았는데 안 바뀐다")
- **영향 범위를 숫자로.** "많이 열림" ✗ → "20건 → 50건" ✓ (프로덕션 조회는 읽기 전용)
- **작업 중 찾은 문제**를 따로 적는다. 리뷰어가 가장 보고 싶은 부분이다
- **확인 방법**은 실제 데이터로 — "테스트해보세요" ✗ → "`LT-2025-0140` 열어서" ✓
- 기획 문서는 **링크**로. 본문에 복제하면 갈린다

## 6. 순서

```
1. check.sh                      → 사실 확인
2. 뒤처졌으면 rebase → 검증 재실행
3. 검증 (테스트 + 빌드)           ← 여기서 멈추는 게 dev 깨뜨리는 것보다 낫다
4. 커밋 (레이어 접두사)
5. push
6. PR — 마이그레이션 · 배포 순서 명시
7. mergeable 확인
```

## 하지 말 것

- **사용자가 요청하지 않은 커밋·푸시.** 명시적으로 말할 때만 한다
- 검증 없이 커밋. 특히 FE 는 `vitest` 통과가 빌드 통과를 뜻하지 않는다
- 마이그레이션 유무를 안 적기
- 기존 lint 오류를 내 것으로 착각해 무관한 파일 고치기 (범위 확대)
- PR 본문에 빈 절 남기기 — 없으면 그 절을 지운다
